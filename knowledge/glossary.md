# Foundry glossary — the ubiquitous language

The vocabulary contract for foundry's specs, templates, skills, and concepts. When code
and this file disagree, this file wins (and the code is debt to be migrated).
A new term names its prior art — the industry or stack standard it follows — or
records why none fits.

## Canonical terms

| Term | Definition | Replaces (now debt) |
|---|---|---|
| **Bootstrap** | The one-time act of installing the setup into a consumer repo: inspect → interview → copy → generate → verify. | scaffold (as a verb), init |
| **Consumer repo** | A repo that received the setup via bootstrap. | target repo, client repo |
| **Harness** | An AI coding tool that runs foundry's skills and consumes a bootstrapped repo (Claude Code, Codex, …). Agent-harness-engineering vocabulary: the runtime that wraps an LLM — the model proposes, the harness executes — where skills are one layer. | agent (the tool), host |
| **Harness availability** | The local, user-specific ability to run a manifest-selected harness now: command present, auth valid, network reachable, subscription usable, and not blocked by quota. SRE health-check / availability vocabulary, constrained here to a transient check separate from repo intent. The `harness-status.py` name uses "status" for the stored result object, not a separate concept. | harness health (less precise), subscription state |
| **Broker** | The process that sequences harness turns, records the event ledger, stores payloads, and renders rebuildable views for a harness deliberation session. Message-broker vocabulary, constrained here to a local Foundry runner rather than a network service. | orchestrator, coordinator |
| **Harness deliberation** | A mediated Foundry session where two selected harnesses exchange final-turn artifacts, challenge assumptions, and produce a traceable implementation-ready spec. Prior art: multi-agent debate and deliberation systems; Foundry keeps the repo-facing term **harness** to avoid confusing the tool with the model. | multi-agent debate (too broad), agent room |
| **Participant** | A selected harness instance inside a harness deliberation session. Collaboration / meeting vocabulary, constrained here to non-human harnesses; the human role is **Mediator**. | speaker, agent |
| **Mediator** | The human authority in a harness deliberation session: records decisions, revises dispositions, and decides when the session can generate a spec. Mediation / facilitation vocabulary, constrained here to a command pane and event log. | moderator (too social), arbiter |
| **Deferred dissent** | A non-blocking disagreement the mediator carries into `design.md` as a named tradeoff instead of resolving or dropping it. Coined for Foundry to preserve dissent without blocking spec generation. | unresolved concern, open question (when non-blocking) |
| **Session storage tier** | A harness deliberation storage class: Tier 1 is the append-only event ledger, Tier 2 is immutable payload storage, and Tier 3 is rebuildable views. Event-sourcing and materialized-view vocabulary, constrained here to local session files. | cache (for Tier 3), state file |
| **Template** | A file foundry installs into a consumer repo. Three classes: *verbatim* (byte-identical everywhere, byte-checked), *seed* (copied once, then repo-owned), *generated* (produced per-repo by the bootstrap skill). | boilerplate, scaffold (as a noun) |
| **Seed** | A template copied once at bootstrap and then owned by the consumer repo (board, glossary, doc stubs, rules). Never byte-checked — divergence is the point. Database-seeding vocabulary. | starter, stub (as a class name) |
| **Version marker** | The `foundry-template: <name> v<N>` comment stamped into every verbatim template copy; what `/foundry:update` diffs against. | header, watermark |
| **Gate** | A verification command whose recorded PASS is the evaluator for done-ness. The quick gate runs pre-push and in CI; a heavy gate is optional and repo-specific. | check, validation step |
| **Gate tool** | A Foundry-shipped verbatim script that belongs in a consumer repo's `Gate` (e.g. `check-board.py`, `prose-lint.py`), self-declared by a `# foundry-gate-tool:` marker carrying its literal gate invocation. Both `bootstrap` and `update` wire every marked tool from the marker, so a new one is never a hardcoded list. Prior art: a CI check / pre-commit hook; the marker is a sibling of the `foundry-template:` / `foundry-seed:` markers. Extends the `Gate` term. | — |
| **Gate feedback** | A failed gate’s evidence (command output tail, marker verdict, or missing-path explanation), fed by the driver into the retried stage’s prompt and into review→build loop-back. Closed-loop-control / CI failure-reporting vocabulary; extends the `Gate` term. First attempts carry none — a prompt stays a pure function of (stage, rubrics, card, feedback). | blind retry (the pre-feedback behavior) |
| **Fixture** | A small repo under `evals/fixtures/` that evals run against. xUnit vocabulary. | sample repo, test repo |
| **Seeded defect** | A deliberate fault on a fixture branch (failing test, lint error, debt term) that a generated gate must catch. Grades gates by discrimination, not green-ness. Mutation-testing vocabulary. | mutation, fault injection |
| **COE** | Correction of Error: a dated record of a real failure the setup permitted. Closed only by a mechanical change (gate, lint, rule, or eval fixture). Promotes upstream to foundry when the root cause is shared machinery. AWS operational vocabulary. | postmortem (debt only when used for setup failures), retro |
| **Interview** | The bootstrap's question pass that supplies repo content: description, vocabulary seed, API surface, gate commands, isolation needs, unit of work for logging. | wizard, questionnaire |
| **Manifest** | `.foundry/manifest.json` in a consumer repo: the plugin version, the convention version, the harness set, plus each installed verbatim file's template name, version, and content hash — how `/foundry:update` tells pristine from customized and whether the repo needs migrating. Package-manager vocabulary (lockfile family). | lockfile (for this file), state file |
| **Wide event** | One structured record per unit of work carrying identity, release metadata, execution cost, and decision inputs — the canonical log line. The logging convention bootstrap installs. Stripe/Honeycomb vocabulary. | log spam (many fragmented lines per request) |
| **Card / Board** | One row of work on `roadmap/ROADMAP.md` / the board itself — the single source of truth for cross-spec status. | ticket, issue (for board rows) |
| **Card id** | A card's unique, slug-safe (`^[a-z0-9][a-z0-9-]*$`) handle in the board's `Id` column — required on claimable cards and enforced by `scripts/check-board.py`. Names the card's branch/worktree (`card/<id>`, `wt/<id>`). Database primary-key vocabulary. | slug, key, name (for the Work title) |
| **Arm** | A navigation condition under test in an eval; the same task runs under each arm (full-load, native Read/Grep, knowledge.py disclosure). Experimental-design / A-B-testing vocabulary. | variant, condition |
| **Gold span** | The document section(s) an answer requires — the navigation eval's ground truth, listed in `answer-key.json`. Information-retrieval (gold / ground-truth) vocabulary. | golden answer, expected section |
| **Context recall** | The fraction of an answer's gold spans an arm loaded into context — the completeness axis. RAG-evaluation (RAGAS) vocabulary. | coverage |
| **Context cost** | The context tokens a run loads to reach its answer — an eval's efficiency axis. | token cost |
| **Decoy** | A near-duplicate but wrong span (or finding) planted in a fixture; an arm whose answer relies on it scores a decoy hit, testing discrimination. Established in the reviewer fixture. | distractor, trap |
| **Verified finding** | A code-review finding an executor *ran and reproduced*; it may block. Test-driven verification / proof-by-reproduction vocabulary. | proven finding |
| **Hypothesis finding** | A code-review finding inferred by reading but not reproduced by execution (non-executable, or not cheaply runnable); advisory only, never blocking. The scientific hypothesis (unproven until tested). | unverified finding |
| **Executor** | How a checkable finding is run to verify it: its existing test, a repro snippet, or `lldb` (the `debug` skill) for a native fault — one component behind a `verified\|refuted\|unrunnable` contract (`verify-finding.sh`). Strategy "executor" / test-runner vocabulary. | verifier, check runner |
| **Concept** | A single unit of knowledge — one markdown file under `knowledge/`, carrying a `type`. Open Knowledge Format vocabulary. | doc, document, page |
| **Type** | A concept's class in frontmatter: one of `reference`, `architecture`, `guide`, `decision`. The OKF required field; foundry keeps it a closed set. | kind, category |
| **Convention version** | A monotonic integer in `.foundry/manifest.json`, bumped only by a *convention break* — a release that renames templates, moves directories, or changes frontmatter. Independent of plugin semver (the 0.x reset made semver useless for ordering); drives which migrations `/foundry:update` applies. Angular `ng update` / schematics migration-version vocabulary. | — |
| **Signal** | One observation the self-improving loop ingests — an eval metric, a code/spec-review finding, a dogfood failure, or a GitHub issue — carrying a `source_kind`. Its raw payload lives in the gitignored raw zone; only a generic summary and a hash-ref reach the committed ledger. Observability / event-pipeline vocabulary (a signal as a raw input event), constrained here to loop inputs. | finding (too narrow), event (overloaded by the broker's ledger) |
| **Candidate** | A durable, generic problem the loop aggregates from recurring signals, fingerprinted on the normalized cause (`source_kind + invariant + failing_signature + affected_surface`) — the machine-readable, pre-COE sibling of a COE. Lives committed in the ledger. Bug-triage / candidate-fix vocabulary, constrained here to a committed aggregate problem record. | issue (GitHub-overloaded), cluster |
| **Metric** | A numeric eval sample the loop ingests over time — fixture, run, recall, decoy count, pass/fail — the trend a candidate's score reads. Recorded as `metric_observed` in the shape `evals/harness/score_review.py` emits. Telemetry / time-series-metric vocabulary, constrained here to eval samples. | measurement, score (reserved for ranking) |
| **Candidate ledger** | The committed, generic-by-construction store under `.foundry/state/self-improvement/` holding the loop's candidate and metric history as an append-only event ledger plus a rebuildable digest — the loop's durable, cross-clone memory; raw signals stay in the gitignored raw zone. Accounting-ledger / event-sourcing vocabulary, reusing the broker's *ledger* sense (`Session storage tier`). | candidate database, signal log |
| **Redaction gate** | The single writer of the committed candidate ledger: it rejects any committed-bound record carrying a raw-text marker (path, secret, PII) or one that is duplicate, overfit, private, or out of scope, recording `signal_rejected` and writing nothing. The structural defense against raw-signal leakage; ships with its own discriminating eval. The telemetry opt-in gate also records `signal_rejected` (reason `telemetry-disabled`), so `signal_rejected` is the shared rejection event of both gates. Reuses *redact* from the harness-deliberation adapter (which redacts account identifiers from raw output); *gate* per the glossary `Gate` term. | sanitizer, scrubber |
| **Telemetry opt-in gate** | The check, ahead of the redaction gate, that refuses a `telemetry` signal unless the `telemetry.enabled` flag is ON; refusal records `signal_rejected` reason `telemetry-disabled`. `telemetry` is the one external-contribution `source_kind`; the five internal sources are always on. The flag is a boolean in `.foundry/self-improvement-config.json` — a repo-local config file (the convention of `knowledge/knowledge-config.json` / `knowledge/.vitepress/site.json`; `roadmap/specs/foundry-core/design.md` §Template classes), kept out of the managed `.foundry/manifest.json` lockfile. Opt-in / feature-flag vocabulary; *gate* per the glossary `Gate` term. | telemetry flag, consent gate |
| **Store write lock** | The advisory `flock` on `.foundry/state/self-improvement/store.lock` that serializes the candidate ledger's write critical section (acquire → read view → decide candidate + write-if-absent payload → append → release). The shared signal store (S1) has many concurrent writers, unlike the broker's single-writer per-session `SessionStore`, so it needs the lock the broker does not; reads stay lock-free. Process-level cooperative locking, not an OS guarantee against a writer that bypasses the store API. POSIX advisory-file-locking (`flock(2)`) vocabulary — distinct from the bootstrap gate's machine-global *mkdir*-lock (`generate.md` §Gate wiring), which guards a single-host gate run and needs stale-lock reclaim because it does *not* release on process death, the property this lock relies on. | mutex, file lock, ledger lock |
| **Autonomy level** | How far the `code` lifecycle runs unattended before handing back — Supervised (asks at gates), Guided (asks at decisions), or Autonomous (asks at nothing but hard blockers). Prior art: Codex approval modes (Read-only / Auto / Full Access) and the role-based agent-autonomy levels (operator → observer); foundry binds the level to its lifecycle gates. | — |
| **Stop-point** | The boundary that ends an autonomous `code` run: a feature, a named board card, the current epic, or the roadmap. Debugger-breakpoint vocabulary — a user-set point where automated execution halts and returns control. | — |
| **Driver** | The deterministic state machine that runs the eight-stage `code` lifecycle: compiles stage prompts, invokes harnesses through adapters, evaluates gates as preconditions (never asking the model whether one passed), and records the run ledger. In-repo: skill-hooks research named "a deterministic lifecycle driver" the consensus answer; test-driver vocabulary. | orchestrator (for the lifecycle stages) |
| **Harness adapter** | A per-harness TOML declaring the instruction-file mapping and headless/interactive command templates, backed by a named parser and conformance fixtures that turn harness CLI drift into a red test rather than a runtime surprise. GoF Adapter; extends (not replaces) v1's harness map (`harness-agnostic` spec). | — |
| **Stage prompt** | The prompt the driver compiles for a judgment stage: the stage's rubric(s) plus the card's context — the seam where deterministic code hands off to a judgment-capable harness. Prompt-template vocabulary (LangChain et al.), constrained to lifecycle stages. | — |
| **Stage rubric** | A judgment stage's content contract — intent, invariants, and an output contract the stage's gate parses — never an orchestration verb (worktree, commit, board, push stay driver vocabulary). Assessment-rubric vocabulary (education), constrained to lifecycle stages. | — |
| **Run ledger** | The append-only, gitignored JSONL event log per driver run (`.foundry/runs/<run-id>/events.jsonl`) recording wide events — tokens, cost, gate outcomes — that `--resume` reads to find the last completed stage. Event-sourcing; reuses the in-repo *ledger* sense (`Session storage tier`, `Candidate ledger`). | — |
| **Routing table** | The `.foundry/config.toml` mapping from lifecycle stage to (harness, model, effort), resolved CLI flag > per-stage > default > shipped default — one precedence boundary, per the code-review Defaults rule. Network routing tables; LLM-router systems (RouteLLM). | — |
| **Pinned run** | Executing the foundry CLI at the repo-pinned git tag via ephemeral `uvx` rather than a repo-vendored copy — the zero-install property with one implementation instead of dual-maintained scripts. Pinned-dependency / lockfile vocabulary; `npx`/`uvx` ephemeral execution. | vendored gate-tool scripts, vendoring |
| **CLI shim** | The repo-local `.foundry/bin/foundry` executable every caller (the `code` skill, CI, a human) runs instead of a bare `foundry`: it reads the pin from `.foundry/config.toml` and forwards to the pinned CLI, so the tag lives in one place. Self-host-aware — foundry's own repo runs the local tree. The plugin ships skills only, not the CLI, so the shim is the entry point. Wrapper-script / launcher prior art; extends [[Pinned run]]. | hardcoded `@tag` in the hook, the two-places pin |
| **Materializer** | The deterministic, idempotent code that writes templates into a consumer repo — bootstrap's copy/fill and update's migrations — operating on the glossary's `Template` classes. Build-system "materialize" / materialized-view vocabulary. | — |
| **Conformance fixture** | A recorded real harness transcript under `tests/fixtures/adapters/<name>/` that an adapter's parser must handle; a red one means the harness CLI's output format drifted. xUnit fixture sense — distinct from the glossary **Fixture**, a small repo under `evals/fixtures/` that bootstrap evals run against. | — |
| **Pytest repo fixture** | A minimal git repo under `tests/fixtures/repos/` that unit and smoke tests run against — test-local, never an eval target. Same xUnit family as **Conformance fixture**; distinct from the glossary **Fixture**. | — |
| **Gate suite** | The code-owned check set `foundry gate` runs: the board/prose/knowledge modules (ports of the v1 gate tools) plus the repo's `[gate].commands`. xUnit test-suite vocabulary; extends the glossary **Gate** term with its v2, single-command realization. | — |
